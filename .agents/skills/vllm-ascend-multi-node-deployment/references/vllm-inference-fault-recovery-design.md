# vLLM 在线推理服务故障检测与恢复方案

本文定义已完成部署并通过首次验收的 vLLM 在线推理服务的故障检测与恢复方案，适用于
单机、普通多机和 Prefill/Decode（PD）分离部署。故障判断和恢复验证依据 SSH、Docker、
进程状态、NPU 健康、网络连通性和真实业务请求完成。

## 整体架构和文件目录设计

Skill 只负责部署完成后的初始化和监控进程启动，监控进程负责部署完成后的持续检测与恢复。
监控进程不调用 Agent、LLM 或 Skill，也不根据自然语言临时生成命令。规则、恢复范围和动作
都由代码预先定义。

目录设计如下：

```text
.agents/skills/vllm-ascend-multi-node-deployment/
├── SKILL.md
├── references/
│   ├── common.md
│   ├── multi-node-deployment.md
│   ├── multi-node-PD-disaggregated-deployment.md
│   └── monitor-manifest.md
├── scripts/
│   ├── vllm_fault_monitor.py
│   ├── fault_rules.py
│   ├── fault_actions.py
│   ├── start_fault_monitor.sh
│   └── stop_fault_monitor.sh
└── tests/
    ├── test_fault_rules.py
    └── test_stop_intent.py
```

文件职责：

- `SKILL.md`：部署验收通过后生成监控清单并启动监控进程；向用户返回监控日志和正式停止
  命令。它不负责持续巡检和故障决策。
- `monitor-manifest.md`：定义部署阶段必须固化的数据，包括目标节点、服务角色、容器名、
  端口、rank、设备、挂载、原始启动命令、服务依赖、恢复范围、备用节点和停止意图位置。
- `vllm_fault_monitor.py`：常驻主循环，接收事件监听模块输出并执行轻量状态检查，收集证据，
  调用规则和动作代码，记录结果并继续监控。
- `fault_rules.py`：确定性规则表，将已确认的检测信号映射到故障类型、恢复范围、重试上限
  和升级条件；没有匹配规则时不得自行恢复。
- `fault_actions.py`：确定性恢复动作，在目标运行环境执行原地恢复、容器重建、角色组重建和
  备用节点迁移；所有动作来自监控清单或固定动作模板。
- `start_fault_monitor.sh`：在部署控制宿主机后台启动 Python 监控进程。
- `stop_fault_monitor.sh`：先写入停止意图，再按逆依赖顺序停止目标服务，确认服务停止后让
  监控进程退出。
- `tests/`：验证故障规则匹配、停止意图匹配和恢复动作选择，不连接真实生产节点。

部署完成后由 Skill 生成的运行数据放在部署目录中，不作为 Skill 静态参考文件：

```text
/data/boom/deployment/
├── deployment_report.json
├── commands.log
├── vllm_fault_monitor.py
├── fault_rules.py
├── fault_actions.py
├── start_fault_monitor.sh
├── stop_fault_monitor.sh
├── monitor-manifest.json
├── monitor-state.json
├── stop-intent.json
└── fault-recovery-<timestamp>.json
```

运行文件职责：

- `deployment_report.json`：部署完成后的正式结果，记录实际部署形态、节点和服务映射、
  容器、端口、设备、模型身份、验收结果和最终状态；用于查看部署是否成功，不作为监控
  进程的临时状态机。
- `commands.log`：记录脱敏后的 SSH、Docker、启动、恢复和观察命令及时间；用于审计和
  重现，不作为可直接执行的恢复命令来源。
- `monitor-manifest.json`：监控进程的唯一运行输入，保存已确认的节点、服务角色、容器名、
  端口、rank、设备、挂载、原始启动参数、依赖关系、恢复范围、备用节点和停止意图位置。
  由部署阶段生成，监控运行期间只读。
- `monitor-state.json`：监控进程的当前状态，包括监控是否运行、最近事件、当前故障、恢复
  阶段、重试次数和最近一次验收结果；供外部查看和故障排查，不作为监控进程恢复状态的输入。
- `stop-intent.json`：受控停止的短期意图记录，包含目标节点、角色、容器、请求时间和意图
  状态。监控进程只对匹配的停止意图抑制自动恢复，停止完成后消费或清理该文件。
- `fault-recovery-<timestamp>.json`：一次故障事件的最终记录，保存故障类型、检测证据、
  恢复动作、重试、预计和实际恢复耗时、备用节点以及最终结果。

监控进程只读取 `monitor-manifest.json` 和运行状态，不读取自然语言对话作为决策依据。监控
清单生成并启动监控后保持不变；节点、容器、端口、设备或恢复命令发生变化时，必须停止
当前监控进程并重新部署、生成清单和启动监控。

## 1. 在线故障检测与恢复设计

部署阶段由 Agent 完成一次性初始化：检查目标节点和服务，生成并保存监控清单，固化容器、
进程、端口、设备、挂载、原始启动命令、服务依赖、恢复范围和备用节点等事实，然后在部署
控制宿主机上启动独立的常驻监控进程。监控进程不运行在 Pi 容器内，不调用 Agent、LLM 或
Skill，不临时生成命令，只读取已保存的数据并执行确定性的规则和动作代码。部署控制宿主机
可以是目标节点之一，也可以是独立的管理节点；多机部署只表示目标宿主机有多台，并不要求
控制宿主机与目标宿主机分离。

监控进程通过 SSH 连接计划中的目标宿主机，持续观察本次部署的容器和服务。发现故障后，
由规则表匹配故障类型和恢复范围，调用预先实现的恢复动作并进行验收；正常恢复完成后记录
并报告结果，不等待用户决策。Agent 退出不会影响监控进程继续工作。

### 1.1 监控进程的作用

监控进程是部署完成后留在部署控制宿主机上的控制进程，具体负责：

1. 读取本次部署的服务清单、节点、容器、进程、端口、设备和原始启动命令；
2. 注册目标运行环境提供的事件监听模块，接收服务生命周期、请求、网络、日志和设备信号；
3. 在没有事件覆盖时，对进程、端口、设备或通信状态执行必要的轻量状态探测；
4. 保存运行状态、日志、进程、网络和设备证据，并判断故障类型和影响范围；
5. 根据规则表调用确定性的进程恢复、容器重建、角色组重建或节点迁移动作；
6. 通过 readiness、通信状态和真实 completion 验证恢复结果，并记录和报告结果；
7. 同一部署同一时间只能执行一个恢复动作，其他故障事件等待当前动作完成后再处理；
8. 持久化故障、动作、重试和容器变更记录，监控进程重启后可以继续工作；
9. 在服务正式停止或监控被明确撤销后退出。

### 1.2 故障发现机制

监控进程采用事件驱动优先的方式：优先接收运行时、服务入口、代理、网络、日志或节点健康
组件提供的推送事件。事件监听模块只负责把外部信号转换成统一的故障事件，不在本设计中规定
具体平台或命令。

没有推送事件接口的信号，通过有界的轻量状态探测确认，例如容器和进程存活、readiness、
业务探针、设备健康和最近日志。事件接收与状态探测是两种互补机制，具体采用哪些事件监听模块由
目标运行环境的实现决定。

Docker 事件或兜底探测结果进入监控进程后，按以下路径处理：

```text
接收事件
  ↓
根据部署记录中的节点、角色、服务实例和必要的 rank 定位部署对象
  ↓
读取部署记录并补充运行状态、日志、进程、网络和设备证据
  ↓
判断故障类型和恢复范围
  ↓
匹配故障规则
  ↓
执行恢复动作并验证
  ↓
记录并报告结果
```

纯事件监听无法发现“容器仍在运行但子进程静默退出”这类没有事件上报的故障。因此，监控
进程在没有事件时按实现定义的有界节奏执行兜底检查，只检查容器状态、预期进程是否存在以及
readiness 或端口是否可访问；任一检查异常后，再读取运行日志、进程和设备状态确认故障，
不让 Agent 定时轮询。

监控进程收到事件后，读取部署报告、容器状态、进程、端口、日志和 NPU 证据；具体故障
类型、确认条件、恢复范围和升级条件统一按第 2.1 节判定。没有事件上报的静默故障，则使
用本节前面规定的三项轻量状态检查。

有业务流量时，真实请求的错误和超时是最直接的业务故障信号；没有业务流量时，使用
readiness、端口、进程心跳或必要的最小状态探测发现“进程存在但已经不处理请求”的静默
故障。单次网络抖动或请求超时先记录为可疑状态，连续证据确认后再启动恢复，避免误重启。

### 1.3 监控与恢复闭环

宿主机监控进程按以下流程工作：

```text
读取部署记录
  ↓
监听事件或按需进行兜底探测
  ↓
保存故障证据并确认类别
  ↓
匹配规则并隔离故障服务
  ↓
停止新请求进入故障端点
  ↓
选择单服务、容器、角色组原地恢复或备用节点迁移
  ↓
按原拓扑和原配置重建
  ↓
检查容器、进程、设备、端口、rank、connector 和模型身份
  ↓
从公共入口发送真实 completion
  ↓
记录结果、报告状态并恢复持续监控
```

只有同时满足以下条件才能将服务恢复为 `ready`：

- 计划中的服务和 rank 完整；
- 预期进程、命令、设备、挂载和环境正确；
- 通信端口、Proxy 后端和 connector 正常；
- 模型身份正确；
- 通过公共入口的真实 completion 成功且响应非空；
- P/D 请求期间没有 KV、通信或远端 engine 错误。

### 1.4 用户主动停止服务

Skill 目录中预置 `scripts/stop_fault_monitor.sh`。部署完成并通过首次验收、监控进程启动后，
Agent 将该脚本原样复制到部署控制宿主机的部署目录，并在同一目录生成本次部署的
`monitor-manifest.json`，向用户提供正式停止命令：

```text
/data/boom/deployment/stop_fault_monitor.sh
```

复制到部署目录的脚本内容不因节点、容器或端口变化而修改；脚本按自身所在目录读取同目录
下的 `monitor-manifest.json`。每次部署变化的是监控清单，不是停止脚本代码。

用户主动停止服务时必须执行该命令，流程如下：

```text
执行 stop_fault_monitor.sh
  ↓
原子写入 stop-intent.json
  ↓
按逆依赖顺序通过 SSH 停止目标服务
  ↓
监控进程收到退出事件并匹配节点、角色、容器名和请求时间
  ↓
标记为 intentional_stop，不执行故障恢复
  ↓
确认目标服务全部停止，消费停止意图并退出监控进程
```

这里的 `stop-intent.json` 不是 Docker 停止命令的输入，也不负责决定逆依赖顺序；它只是停止
脚本和独立监控进程之间的持久化通信标记。停止脚本必须先写入该标记，再执行 SSH 停止，
因为监控进程可能先收到容器退出事件。监控进程匹配到标记后，才会把这些退出判定为用户主动
停止并抑制自动恢复。真正的停止顺序仍由 `stop_fault_monitor.sh` 中的固定动作决定。

`stop_fault_monitor.sh` 不是故障恢复脚本，也不由 LLM 临时生成。部署尚未通过首次验收时，
不提供正式在线停止命令；部署失败阶段由部署流程执行清理。用户直接执行 `kill`、`docker
stop` 或删除容器而没有对应的停止意图时，监控进程无法确认用户意图，按未归因退出执行故障
判断和自动恢复。

## 2. 统一故障分类、检测和恢复策略

### 2.1 故障分类、检测和恢复策略

监控进程每次发现异常，都必须从部署记录读取节点、服务、容器、进程识别条件、设备、
端口和原始启动参数；不得猜测 PID、端口占用者或容器归属。每类故障统一保存检测证据，
再按下表选择恢复范围。表中的时间是镜像和模型已经位于目标节点、SSH 和 Docker 可用、恢复
动作可以直接执行时的典型自动处理时间，包括恢复动作和基本验收，不包括首次拉取镜像、下载
模型、物理网络维修、硬件更换和人工修正配置的时间。大模型重新加载时间应在部署验收时测得，
并叠加到相应估算中。

| 故障类型 | 检测信号和确认条件 | 默认恢复范围和策略 | 典型自动恢复时间 | 升级条件 |
|---|---|---|---|---|
| 进程退出 | 容器仍在运行但预期 vLLM 进程不存在；PID 启动时间和命令身份不匹配 | 单进程：使用原命令在原容器、原节点恢复进程 | 30 秒–5 分钟，另加实际模型加载时间 | 进程反复退出、容器环境损坏或原地恢复失败，升级为容器重建 |
| 容器退出或 OOM | `docker inspect` 状态为 exited、OOM 或非零退出；日志包含启动失败或 OOM | 容器：在原节点按原镜像、挂载、设备和命令重建 | 1–10 分钟，另加实际模型加载时间 | 达到重试上限、Docker/运行时异常或设备不可用，升级为节点迁移 |
| readiness 丢失 | API、RPC、控制端口连续不可用；进程仍存在 | 单服务或容器：先隔离入口，再重启或重建对应服务 | 30 秒–5 分钟 | 端口恢复但真实请求仍失败，按进程组或角色组重建 |
| 业务请求失败或卡死 | 真实 completion 超时、空响应或连续失败；无流量时由最小业务探针发现 | 使用 readiness、端口、进程状态和受控的最小业务探针连续确认服务异常后，按原命令重启对应进程或容器，保持原拓扑；不重放用户原始请求 | 1–10 分钟，包含确认和验收时间 | 采样仍无 CPU、NPU、显存和网络进展，升级为角色组重建 |
| 分布式 rank 失效 | rank 数量不完整、通信端口断开、HCCL/TP/DP 错误；只有当前 vLLM-Ascend 版本、镜像和并行模式明确支持安全重加入时，才允许单 rank 恢复 | 默认按角色组恢复：普通多机重建 Master 和全部 Worker，PD 分离重建受影响的 Prefill 或 Decode 组；不能只确认单个 rank 重新运行或端口恢复 | 5–20 分钟，另加实际模型加载时间 | 组重建失败或承载该组的节点故障时，使用备用节点按原拓扑重建受影响通信组；健康节点保持不变，必须通过完整通信检查和真实 completion 才能报告成功 |
| KV connector 或 Mooncake 异常 | connector 初始化、注册、KV 获取/发送或远端 engine 查询失败 | 角色组或单服务：按受影响的 P/D 角色组重建；Mooncake 服务单独故障时先重建该服务 | 2–15 分钟，另加实际模型加载时间 | P/D 重新注册失败，迁移受影响角色组 |
| Proxy 异常 | Proxy 进程退出、入口端口不可用或后端列表丢失 | 单服务：只重建 Proxy，保留健康的 P/D 和 KV 服务 | 10 秒–2 分钟 | Proxy 恢复后真实请求仍失败，重新检查后端角色组 |
| 网络或 SSH 不可达 | SSH、数据面 IP、通信端口或网卡连续不可达 | 节点或整体部署：等待短暂抖动，同时隔离故障端点 | 不固定；短暂抖动通常 1–5 分钟，迁移通常 10–30 分钟 | 节点或链路持续不可用，迁移到通过预检的备用节点 |
| NPU 不健康 | `npu-smi` 健康异常、设备丢失、驱动或 HCCL 报错 | 节点或整体部署：隔离使用故障设备的服务，不执行自动芯片 reset | 有备用节点时通常 10–30 分钟；无备用节点时无法自动恢复 | 有等价备用节点则迁移；没有则报告降级或失败 |
| 宿主机不健康 | SSH 失败、Docker/Ascend 运行时不可用或关键目录不可读 | 节点或整体部署：不在故障宿主机上无限重试 | 有备用节点时通常 10–30 分钟；无备用节点时无法自动恢复 | 迁移该节点上的服务或报告失败 |
| 配置、镜像或模型错误 | 参数互斥、挂载缺失、镜像 digest 不一致、模型加载失败、端口冲突 | 不恢复：停止自动重试并保留完整证据 | 不自动恢复 | 由用户修正部署计划后重新部署 |
| 资源耗尽 | 显存、KV Cache、磁盘、端口或设备资源不足 | 单服务或容器：不自动缩小 TP/DP/PP/EP；可清理本次残留后重试一次 | 清理重试通常 1–10 分钟；迁移通常 10–30 分钟 | 仍不足则使用已声明的等价备用节点或报告失败 |

网络和 SSH 短暂失败先按连续确认次数等待，不直接执行迁移；确认达到阈值后才进入迁移或
终态报告，避免每个探测周期生成一条未配置动作的故障记录。恢复动作按固定链路升级：
进程重启失败后重建容器，容器重建失败后重建角色组，角色组仍失败后迁移到备用节点；
迁移失败后停止自动重试并报告终态。

恢复命令返回成功只表示动作已被目标宿主机接受。监控进程随后通过容器、进程、readiness、
受控业务探针和 NPU 检查完成恢复验收；只有验收通过才将恢复记录标记为 `recovered`。
事件触发后的日志读取用于设置 connector/KV 错误信号，不能只依赖退出码判断 connector 状态。

### 2.2 当前支持的恢复范围

| 范围 | 说明 |
|---|---|
| 进程原地恢复 | 在原宿主机、原容器或原服务实例中恢复 vLLM 进程 |
| 容器原地重建 | 在原宿主机使用原镜像、原设备和原命令重新创建容器 |
| 角色组重建 | 同时重建一个分布式通信组，例如全部 Worker、Prefill 或 Decode |
| 备用节点迁移 | 将受影响服务迁移到预先声明且通过预检的备用宿主机 |
| 恢复后验证 | 通过 readiness、通信检查和真实 completion 判断是否恢复 |

### 2.3 原地恢复

同时满足以下条件时优先原地恢复：

1. SSH 和 Docker 仍然可用；
2. 所需 NPU 健康，设备数量和设备身份未改变；
3. 镜像 digest、模型目录、挂载、端口和网络仍可用；
4. 故障不属于持续的宿主机、网络或 NPU 故障；
5. 恢复不改变 TP、DP、PP、EP、rank 和服务拓扑。

原地恢复使用部署记录中的原镜像、原挂载、原设备、原环境变量和原命令。恢复动作必须
验证 Boom 所有权、容器身份和进程命令，不得使用 `pkill`、宽范围 `docker rm` 或端口占用
者推断所有权。

### 2.4 备用节点迁移

以下情况升级到备用节点：

- NPU 健康持续异常；
- 宿主机或关键网络持续不可达；
- Docker 或 Ascend 运行时损坏；
- 同一恢复范围达到最大尝试次数；
- 原节点无法提供原拓扑所需的设备数量。

备用节点必须在部署前声明并通过 SSH 权限、Docker、镜像 digest、Ascend 挂载、等价 NPU
型号和数量、网络、模型路径、端口、日志目录及设备占用检查。迁移不能通过缩卡或改单机
拓扑来伪装成恢复成功。

迁移后需要重新生成节点相关值，例如通信 IP、网卡、设备列表、rank 地址、Proxy 后端、
KV 端口和 Mooncake 地址；模型、镜像、并行规模和服务角色保持不变。

## 3. 普通多机与 PD 分离的范围差异

| 部署形态 | 主要检查对象 | 故障后的默认恢复范围 |
|---|---|---|
| 单机 | 服务进程、容器、设备、API 和真实请求 | 单服务或容器原地恢复；设备/宿主机故障时迁移整套服务 |
| 普通多机 | Master、全部 Worker rank、通信端口和公共 API | Master 或 rank 组异常时重建对应通信组；节点故障时迁移受影响组 |
| PD 分离 | Proxy、Prefill、Decode、P/D rank、KV connector 和可选 Mooncake 服务 | Proxy 单独恢复；P 或 D 按角色组恢复；KV 服务异常时连同相关角色重新注册 |

恢复顺序遵循部署依赖关系：停止或隔离入口后，重建底层通信和角色服务，最后恢复入口并
发送真实请求。启动顺序仍以对应部署文档为准。

## 4. 故障记录

故障确认、恢复动作和恢复结果统一以 JSON 持久化，至少包括发生时间、受影响的节点和服务、
故障现象与检测证据、采取的恢复动作、重试情况、是否使用备用节点以及最终验证结果。
